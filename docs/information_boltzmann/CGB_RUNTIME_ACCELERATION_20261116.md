## 为什么保留这三项

**1. 同一后验只分解一次矩阵。** 原`evidence_correction`分别求均值、预测不确定性，`mechanism_hypotheses`又为算子假设分解同一核。现在同一个后验返回LU因子，合并均值/不确定性的右端项，再把同一因子用于假设。没有跨事实、参数版本或优化更新缓存分解。普通公开四返回值接口保持原操作，实际posterior选择共享分解接口。CPU/CUDA、空支持和真实8条支持的前向与相关导数通过对齐。

同进程交替测真实关系：单条支持小项约1.88倍，8条支持约1.38倍。它是关系求解小项的加速，不是全轮加速。

**2. 单次1036字节输入传输。** 当前字节int64、256项FP32快表logp、FP32剩余预算共享一块对齐的固定缓冲；CUDA图保留原dtype视图。CPU先写入1KiB锁页缓冲，再同步完成一次上传，避免临时GPU张量、转换及分散填充。问题向量仍实时送入，训练/非捕获路径保持原实现。同步完成上传后才允许主机重用缓冲，所以无逐字回读的基准循环也没有异步覆盖风险。

同一实际身体128字节解码的交替中位数0.6967→0.6507秒（约7%），另一组约5%。普通生成、连续状态、live问题/预算和事实缓存刷新均检查通过。

**3. 哈希在文件写入时计算。** SHA256覆盖实际gzip头、压缩数据及尾部；字节先成功写出，再更新摘要。完整文件关闭后才完成原子发布及hash绑定sidecar，省掉保存后再次通读约0.8GB。gzip/torch数据格式、每轮完整停存及旧文件恢复保持不变，未增加全量后台副本。数值回归直接比较实际文件SHA并禁止新路径再次调用读文件哈希；故障仍不发布未完成文件。

同进程ABBA等交替保存的中位数4.484→4.232秒，I/O负载影响较大。确定减少的是一次完整文件重读；未承诺每次都节省同样秒数。
